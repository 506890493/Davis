# Davis 项目问题排查流程

## 核心原则

**从现象出发，逐层追溯，找到根因再动手。** 不要猜测，要验证。

## 排查步骤

### 第 1 步：明确现象
- 用户报告了什么？哪个页面、哪个操作、什么预期 vs 实际？
- 能否稳定复现？是否有特定条件？

### 第 2 步：前端 → 后端数据流追踪

按以下链路逐层检查：

```
前端页面（Vue 组件）
  → API 调用（ruoyi-ui/src/api/system/*.js）
    → 后端 Controller（ruoyi-admin/.../controller/davis/）
      → Service 实现（ruoyi-system/.../service/impl/）
        → Mapper 接口 + XML（ruoyi-system/.../mapper/）
          → 数据库表（sql/davis.sql）
```

每一步确认：
- 前端：传了什么参数？API 函数是否正确？
- Controller：端点路径、权限注解、请求方法是否匹配？
- Service：业务逻辑是否正确？是否被后处理覆盖了值？
- Mapper：SQL 是否正确？查询条件、字段映射是否完整？
- 数据库：表结构、字典数据、字段类型是否匹配？

### 第 3 步：常见问题模式

| 症状 | 常见根因 | 检查点 |
|------|---------|--------|
| 前端不显示数据 | 字段被 Service 置空 | ServiceImpl 中是否有针对角色/条件的 `setXxx(null)` 逻辑 |
| 状态显示不一致 | 前后端字典映射错误 | `sys_dict_data` 表中 `dict_value` 是否与前端 `dict.type.xxx` 匹配 |
| 操作按钮缺失 | `v-if` 条件不满足或操作列缺失 | 模板中按钮的显示条件、操作列是否有条件渲染 |
| 通知不推送 | 通知创建逻辑缺失或通知类型错误 | `notificationService.createNotification()` 调用位置、`notification_type` 字段长度 |
| 合同编号重复 | 并发插入 | 检查是否有唯一索引、编号生成是否在事务内 |
| 审批后状态不更新 | 状态字段混用 | `auditStatus`（审核流程）vs `status`（合同生命周期）是否混淆 |

### 第 4 步：使用本次对话中的排查案例

#### 案例 1：审批通过后合同从列表消失
- **现象**：审批通过合同后，列表页看不到该合同
- **追踪**：前端 radio 将 `contract_type` 从 `0`/`1` 改成了 `"1"`/`"2"`，后端审批写入时未传原值，导致被覆盖为 `"0"`
- **根因**：`updateCmsContract` 是全字段更新，审批请求中 `contractType` 为 null 时被默认值覆盖
- **修复**：修复前端 radio 值和后端默认值的一致性

#### 案例 2：合同详情审批后仍显示"待审批"
- **现象**：合同已审批通过，详情页状态仍显示黄色"待审批"
- **追踪**：详情页将 `auditStatus` 和 `status` 混在一个字段展示，且缺少对 `auditStatus='2'` 的处理
- **根因**：UI 层将审批状态和合同生命周期状态混在一起
- **修复**：拆分为"审核状态"和"合同状态"两个独立字段

#### 案例 3：催收任务无法创建
- **现象**：用户找不到创建催收任务的入口
- **追踪**：前端页面有完整的派发方法、对话框、API 调用，但操作列缺少触发按钮
- **根因**：操作列只在 `isPendingPage` 模式下渲染，主列表缺少操作列
- **修复**：为主列表模式新增操作列，添加"催收"按钮

### 第 5 步：写计划并修复

1. 将根因分析和修复方案写入 `docs/davis/plan/` 目录
2. 计划应包含：问题根因、修复方案、影响范围、验证方法
3. 用户确认后执行修复
4. 验证修复效果
